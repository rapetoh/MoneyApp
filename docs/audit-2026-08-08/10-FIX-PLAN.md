# Fix plan

**Source:** the eight verified audit files in this directory (`01`–`08`), 314 findings — 34 Critical, 99 High, 130 Medium, 51 Low.
**Shape:** 45 work items in 5 stages, ordered by dependency.

## How to read this

**The order is a dependency order, not a severity order.** A Critical finding that sits on top of a missing primitive is scheduled *after* that primitive, because fixing it first means fixing it twice. Three interlocks drive most of the sequence:

- **The recurring FK race (`03-F1`) must not be fixed before the sync engine can report failure (`07-F4`, `07-F5`).** Today `createTransaction` hard-codes `return { error: null }` and `createRule` answers a foreign-key violation with `console.warn`. Fix the race alone and the next write that fails — a poisoned queue entry, a CHECK violation, an expired JWT — becomes the new silent failure. The engine has to be able to say "no" before anything is allowed to depend on it saying "yes".
- **The recurring aggregations must be correct *before* rules can exist (`03-F2`, `05-F3`, `05-F19`).** `computeUpcomingRecurring` sums every active rule regardless of `direction` and adds the result to *spend*. Onboarding creates a `direction: 'credit'` salary rule. The only reason no user has ever seen "$4,092 spent" on a $2,000 budget is that `recurring_rules` has zero rows. Ship rule creation first and the app gets measurably worse for every user who onboarded with an income.
- **The calendar month bug (`04-F1`, `05-F1`, `07-F2`, `08-F1`) must not be fixed before there is a canonical timezone convention (`04-F4`).** The RSC boundary is only the visible edge of it: the same page currently computes "August" three different ways (Vercel-UTC, browser-local, device-local), `profiles.timezone` has never been written by any code path, and there are nine hand-rolled month-window implementations. Patch `Calendar.tsx` on its own and you have fixed one of thirty call sites and left the other twenty-nine to drift.

Two smaller ordering constraints, both stated by the auditors and both easy to get backwards:

- **`03-F12` before `03-F10`.** Making mobile anchor accepted patterns on `lastSeenAt` (F10) is correct — but it introduces backdated `last_generated`, which back-generates duplicates of charges the user already logged (F12). Fix the duplicate guard first.
- **`06-F9` before `06-F28`.** Making `client_id` the real idempotency key is correct — but today *any* `23505` is treated as a recurring-dedup conflict and silently soft-deletes the user's transaction. Fix the predicate first or the refactor starts deleting data.

**The counts below are de-duplicated.** Eight auditors reached the same defects from eight directions, so a single bug carries up to six ids: the recurring FK race is `02-F6` = `03-F1` = `06-F1` = `07-F1` = `08-F2`; the mobile `Money` default is `01-F6` = `05-F4` = `07-F3` = `08-F4` = `03-F38`; the 200-row pull cap is `05-F20` = `06-F15` = `07-F44` = `08-F24`. Every item lists **all** the ids it closes, across all eight files, so the owner can verify by id rather than by description. The 133 Critical + High findings resolve to 45 items; the Coverage check at the end maps every one of them.

**Where a patch would stack, the item says so and describes the target design instead.** The owner has rejected patch-stacking; several findings are explicitly the *result* of previous patches (`edit.tsx`'s two-direction rule lookup, `resetDeadLetterEntries()`, `createRule`'s `console.warn`, the `_nonce` router param). Those are called out as such and removed, not extended.

## Stage 0 — Stop the bleeding (do before anything else)

Nine items. Each is independently deployable, depends on nothing in this plan, and either leaks a credential, corrupts data, or blocks the ability to verify any later stage. None of them requires a foundation to exist first.

### 0.1 Rotate the Supabase secret key and move the cron credential into Vault
- **Resolves:** `03-F14`
- **Depends on:** nothing
- **Why now:** a plaintext `sb_secret_…` key with full RLS bypass for every user's financial records is sitting in `cron.job.command` in the production database, where it lands in every logical backup and every support export. It is not a JWT — remediation that assumes `service_role` token semantics will be wrong.
- **Change:** Rotate the secret key in the Supabase dashboard. Store the new value in Supabase Vault (`vault.create_secret('generate_recurring_key', …)`). Re-create cron job id 1 so the command reads `select decrypted_secret from vault.decrypted_secrets where name = 'generate_recurring_key'` at call time instead of embedding a literal. Check the schedule into the repo as a migration — it currently exists only in the production database and in a comment, so a project restore silently loses the whole recurring generator. Rewrite the recipe comment in `generate-recurring/index.ts:6-12` so the next person cannot paste a literal key.
- **Surfaces to update:** `supabase/functions/generate-recurring/index.ts:6-12`, new `supabase/migrations/013_cron_schedule.sql`, the live `cron.job` row, the Edge Function's `SUPABASE_SERVICE_ROLE_KEY` env binding.
- **Done when:** `select command from cron.job` contains no `sb_secret_`/`eyJ` substring, the job's last run in `cron.job_run_details` is a success after rotation, and a fresh environment built only from `supabase/migrations/` has the schedule.
- **Regression test:** CI check failing if `select command from cron.job` matches `sb_secret_|service_role|eyJ`.

### 0.2 Close the open `sync_operations` INSERT policy and revoke the anon grants
- **Resolves:** `06-F4`, `06-F23`, `06-F35`
- **Depends on:** nothing
- **Why now:** `CREATE POLICY … FOR INSERT WITH CHECK (true)` with no `TO` clause defaults to `PUBLIC`, and `anon` holds the INSERT grant. The publishable key ships in every client bundle by design, so anyone holding it can write unbounded rows into the production database with no session.
- **Change:** New migration: `DROP POLICY "Service role can insert sync operations" ON public.sync_operations` (service-role bypasses RLS and never needed a policy). `REVOKE INSERT, UPDATE, DELETE, TRUNCATE ON public.sync_operations, public.ai_usage_log FROM anon, authenticated`. While in the same migration: `ALTER FUNCTION public.handle_new_user() SET search_path = public, pg_temp` and the same for `public.set_updated_at`; `REVOKE EXECUTE ON FUNCTION public.handle_new_user(), public.bump_ask_conversation_last_message() FROM anon, authenticated, public`; add the missing `profiles` DELETE policy for consistency. Enable leaked-password protection in Auth settings and move `pg_net` out of `public`.
- **Surfaces to update:** new `supabase/migrations/014_rls_hardening.sql`; `supabase/migrations/001_initial_schema.sql:226-236` (superseded, leave in place); Supabase Auth dashboard settings.
- **Done when:** `pg_policies` shows no `with_check = true` row on any table in `public`, `information_schema.role_table_grants` shows no write grant to `anon` on `sync_operations` or `ai_usage_log`, and `get_advisors(security)` returns no `function_search_path_mutable` warning.
- **Regression test:** A policy test that attempts `insert into sync_operations` with the anon key only and asserts 401/42501, not 201.

### 0.6 Fix the local SQLite migration that drops the FX columns it just added
- **Resolves:** `03-F3`, `06-F6`
- **Depends on:** nothing
- **Why now:** on the first launch after upgrading from any pre-`67b3858` build — that is, every current TestFlight tester — `migrateSchema` adds the three FX columns and then rebuilds `transactions` from a hard-coded column list that omits them. Every `upsertTransaction` for the rest of that session throws, so the spinner on Save hangs and nothing is stored; `runRecurringCatchUp` aborts mid-loop on an unhandled rejection. This corrupts the core flow *today* and must not be sitting underneath the sync-engine rebuild.
- **Change:** Architectural, not a reorder. Replace the `PRAGMA table_info`-sniffing `migrateSchema` with a numbered migration runner keyed on `PRAGMA user_version`: each step is a pure `(db) => Promise<void>` applied exactly once, in order, inside a transaction, with `user_version` bumped on success. Build any table rebuild's `CREATE TABLE`/`INSERT … SELECT` from one canonical column manifest shared with `initSchema` and with `upsertTransaction`'s INSERT list, so the three can never drift again (this is also the root of `06-F16`, fixed in 1.6). As the immediate correctness fix inside that runner, the `payment_method` rebuild runs *before* the FX `ADD COLUMN` loop and its column list includes all three FX columns.
- **Surfaces to update:** `apps/mobile/src/services/sync/localDb.ts:72-145`, `apps/mobile/src/services/sync/transactionStore.ts:52-77`, `apps/mobile/src/services/recurringCatchUp.ts:115` (add the try/catch the fire-and-forget call needs).
- **Done when:** a SQLite file built with the pre-`67b3858` schema (`payment_method TEXT NOT NULL DEFAULT 'cash'`, no FX columns) survives `getDb()` with all three FX columns present *and* a full `upsertTransaction` round-trip succeeding in the same session.
- **Regression test:** Exactly that: construct the legacy DB fixture, run `getDb()`, assert `PRAGMA table_info(transactions)` contains the FX columns and that a write succeeds without a relaunch.

### 1.3 One definition of "a day", "a week" and "a month"
- **Resolves:** `04-F4`, `04-F10`, `04-F17`, `04-F29`, `04-F30`, `04-F32`, `06-F11`, `07-F14`, `07-F37`, `05-F16` (the primitive half)
- **Depends on:** 1.2
- **Why now:** `profiles.timezone` is declared in the schema, declared in the type, and written by nothing — all six production profiles read `'UTC'` while the tester is in US Central. With no authoritative zone, thirty call sites across sixteen files each picked their own: Vercel-UTC on server components, browser-local on client components, device-local on mobile, and `AT TIME ZONE 'UTC'` in migrations 008 and 011. The week starts on Monday in seven places and Sunday in three. **Every date finding in this audit is downstream of this item**, which is why it precedes the calendar fix, the budget fix, the export fix, the recurrence engine and the AI windows.
- **Change:** Three parts.
  1. **Capture the zone.** `Intl.DateTimeFormat().resolvedOptions().timeZone` on web/desktop, `expo-localization`'s `getCalendars()[0].timeZone` on mobile (already a dependency), written through `updateProfile` on every authenticated launch — zones change when people travel. Add a read-only "Time zone" row to both Settings screens.
  2. **Build the module.** New `packages/shared/src/utils/period.ts`, the only place in the repo permitted to touch calendar getters: `monthBounds(monthIso, tz)` and `periodBounds(period: BudgetPeriod, atInstant, tz, anchor)` returning **half-open** `[startUtc, endUtcExclusive)` ISO instants (which removes the `23:59:59.000` vs `.999` class of defect entirely); `localDay(instantIso, tz)` → `YYYY-MM-DD`; `localParts(instantIso, tz)` → `{y,m,d,weekdayIndex,hour}`; `monthIso(instant, tz)`; `currentMonthIso(tz)`; `weekStart(instant, tz)`; and one exported `WEEK_START = 1` (ISO Monday) with weekday labels derived from `Intl.DateTimeFormat(locale, {weekday:'narrow'})` rotated by it — which also deletes the four hardcoded Sunday-first `history.weekday_labels` strings that are wrong for fr/es/pt. Delete `packages/shared/src/utils/date.ts` (dead code, wrong shape — it takes no zone).
  3. **Store the resolved day.** Migration adding `transactions.local_day date NOT NULL`, written once by whichever client creates the row and never recomputed by a reader, backfilled from `transacted_at` at the profile's zone.
